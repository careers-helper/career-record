# Role: Meridian Consulting — Java Developer (Sep 2010 – May 2013)

## Snapshot
- **One-liner:** Graduate-entry Java consultant delivering enterprise applications for financial services and public sector clients across multiple short-cycle engagements.
- **Scope:** Individual contributor on client project teams, progressing from supervised pair-programming to independently leading small work packages.
- **Team / org context:** Mid-size UK technology consultancy (~200 people) placing consultants on 3–6 month client engagements, predominantly enterprise Java delivery.
- **What success looked like:** Reliable delivery on client projects, growing independence over time, and building sufficient breadth across the Java/Spring ecosystem to be deployable across different client contexts.

## Context & constraints

This was Elena's first role after graduating from the University of Leeds (BSc Computer Science, 2010). Meridian Consulting operated a consulting model in which developers were placed on client sites for engagements typically lasting three to six months. The work was dictated by client needs rather than any long-term product roadmap, which meant frequent context-switching between domains, codebases, and teams.

As a graduate entrant, Elena joined under the title "Graduate Developer" and was promoted to "Java Developer" after approximately twelve months. The consulting model meant that technical growth was breadth-oriented — exposure to many different systems, patterns, and client environments — rather than depth in any single product or domain. Client site travel from the Reading office was a routine part of the role.

The technology stack across engagements was consistently enterprise Java (Spring, Hibernate, Oracle/MySQL), with frontend concerns typically treated as secondary. This structural under-investment in frontend quality across enterprise Java projects became a recurring observation during Elena's time at Meridian and ultimately influenced her subsequent career direction.

## Core responsibilities

Day-to-day work consisted of delivering Java/Spring components on client project teams under the direction of Meridian delivery leads and client project managers. In the first year, this was predominantly pair-programming with senior consultants, learning enterprise patterns and the consulting delivery model. By the second and third years, Elena was taking ownership of small work packages and delivering independently.

Responsibilities included writing and maintaining backend services, batch processing components, and database access layers. On some engagements, this extended to full-stack work including JSP/Servlet-based frontends and jQuery UI components. Elena also participated in Meridian's internal graduate training programme, eventually contributing back to it through tech talks and mentoring.

## Initiatives

### Client project: Insurance claims processing system

**Problem**
A mid-size insurer required batch processing components for their claims processing system. This was a standard enterprise Java delivery engagement.

**What I did**
Built batch processing components in Java/Spring as part of the client project team. This was Elena's first production code. She paired extensively with senior consultants throughout the engagement, learning enterprise patterns including dependency injection, the DAO pattern, and service layer architecture.

**Technical details**
Java 7, Spring Framework, Hibernate, Oracle DB, JUnit, Mockito, Maven, SVN. Standard enterprise layered architecture with batch processing jobs, service classes, and data access objects.

**Outcome**
Delivered working batch processing components to the client. The primary personal outcome was foundational competence in enterprise Java patterns and the consulting delivery model. No independently notable business outcome beyond successful delivery as a junior team member.

### Client project: Local authority planning portal

**Problem**
A local authority needed maintenance and extension work on a JSP/Servlet-based planning application. The existing frontend code — jQuery-based UI components — had accumulated without clear structure or consistent patterns.

**What I did**
Full-stack work: backend Java changes alongside maintaining and extending the jQuery-based frontend. This was Elena's first meaningful frontend work. She began to notice that the frontend code was treated as an afterthought relative to the backend Java components and started advocating within the team for better structure in the JavaScript layer.

**Technical details**
Java 7, JSP/Servlets, jQuery, Spring Framework, MySQL, Maven, SVN. The frontend was a mix of inline scripts and loosely organised jQuery modules without a consistent architectural pattern.

**Outcome**
Delivered the required changes to the planning portal. The more significant personal outcome was the recognition that frontend code in enterprise Java projects was consistently under-invested in — a pattern Elena would observe repeatedly and which began to shape her professional interests.

### Client project: Pension fund administration system

**Problem**
A pension fund required a greenfield internal administration tool. The project included both backend Java work and a frontend built using AngularJS (v1.x), which was relatively new at the time.

**What I did**
Contributed backend Java components and gained early exposure to AngularJS on the frontend. This was Elena's first encounter with a structured JavaScript framework — as opposed to the ad-hoc jQuery patterns she had seen previously — and the experience of working with a framework that imposed architectural discipline on frontend code was formative.

**Technical details**
Java 7, Spring Framework, AngularJS 1.x, Oracle DB, Maven, Jenkins, JUnit. The AngularJS frontend used controllers, services, and directives in a conventional v1.x structure.

**Outcome**
Delivered contributions to both the backend and frontend of the administration tool. The AngularJS exposure sparked a sustained interest in frontend architecture and directly influenced Elena's decision to pursue frontend-oriented roles after leaving Meridian.

### Internal: Graduate training programme participation and contributions

**Problem**
Meridian ran an internal graduate training programme for incoming developers. As Elena progressed, there was an ongoing need for more experienced graduates to contribute knowledge back to the programme.

**What I did**
Delivered two internal tech talks — one on jQuery best practices and one on AngularJS — drawing on experience from client engagements. In her third year, Elena mentored one incoming graduate, providing pairing support and context on the consulting delivery model.

**Technical details**
Informal knowledge-sharing format: internal presentations and one-to-one mentoring. No formal training curriculum ownership.

**Outcome**
Contributed to the development of one incoming graduate. The tech talks were internal only, with no broader organisational impact beyond the immediate audience.

## Tech & skills used

Core technology across engagements was Java 7 with Spring Framework and Hibernate for backend development, using both Oracle DB and MySQL depending on the client. Frontend work involved JSP/Servlets and jQuery on earlier projects, with AngularJS 1.x exposure on the pension fund engagement. Build and CI tooling was Maven with Jenkins. Version control was SVN throughout. Testing used JUnit and Mockito. Development was done in Eclipse IDE. The consulting model itself required adaptability to different client environments, codebases, and ways of working on short cycles.

## Stakeholders & influence

Elena's primary working relationships were with fellow consultants on project teams, Meridian delivery leads who managed client relationships and project staffing, and client project managers who directed day-to-day priorities. Influence was limited to team-level contribution and, in the later stages, informal advocacy for better frontend code quality. There was no authority over technical direction, staffing, or architectural decisions. The mentoring of one incoming graduate in the third year represented the extent of any developmental responsibility.

## Positioning notes

This was a formative consulting role that built breadth across enterprise Java delivery but not sustained depth in any single system or domain. The client-hopping pattern — four engagements in approximately two and a half years — is characteristic of mid-size consultancy work and provided broad exposure at the cost of ownership continuity.

The most significant outcome of this period was not any individual project delivery but rather Elena's growing recognition that frontend development was consistently under-invested in across enterprise Java projects. The jQuery work on the planning portal highlighted the problem; the AngularJS exposure on the pension fund project demonstrated that structured frontend architecture was possible and valuable. This combination directly influenced her next career move towards frontend-oriented roles.

The progression from "Graduate Developer" to "Java Developer" after approximately twelve months was a standard internal promotion within Meridian's grading structure, not an indication of exceptional advancement.
